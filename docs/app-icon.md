# The app icon is the black tile

Status Trio ships three icon surfaces, and macOS asks a different one of each:

| Surface | Source | Follows the system's icon style |
| --- | --- | --- |
| Menu bar | `StatusIconRenderer`, drawn per appearance at render time | yes |
| Dock while running | `DockIconRenderer` via `AppIconController` | yes — the app resolves the background itself |
| Dock while not running, Finder, Launchpad, Spotlight | `Support/AppIcon.icns` | no — it is one image |

The third surface is the black tile, in every appearance. That is a decision, not
an oversight, and this note records why the obvious alternative does not work.

## Why it is the black tile

The black tile is the app's design: `Support/AppIcon.png` is a dark rounded
square with the white foreground glyph, generated by `AppIconPreview` from
`DockIconRenderer` so the static icon and the running one are the same drawing.
It is also what the Dock draws while the app runs in dark mode, which is where
the icon is seen most.

It does **not** follow the system's light and dark icon style. In light mode the
Finder, Launchpad and the Dock while the app is not running show the black tile,
while the Dock of the running app draws a light one. That mismatch is inherent
to a single-image bundle icon.

## Why it cannot follow the system

Since macOS 26 the system themes an app icon only from an asset catalog carrying
an **icon stack** with one rendition per appearance (`NSAppearanceNameAqua`,
`NSAppearanceNameDarkAqua`, `ISAppearanceTintable`). Two routes were tried, and
both were measured rather than guessed at:

**1. An `AppIcon.appiconset` with `luminosity: dark` entries.** actool compiles
it without an error and then silently drops the dark rendition. Verified against
this project's own artwork, at both a 15.0 and a 26.0 deployment target, with a
one-image and a full twenty-image size matrix; the catalog came back with a
single appearance-less `Icon Image` every time.

**2. A hand-authored Icon Composer `.icon` document.** This does compile — with
`icon.json` plus an `Assets/` directory spelled with a capital A, `actool`
produces the three icon stacks a themed icon needs, and the bundle icon then
does come from `Assets.car`. But the rendition is the same in every appearance:

- `image-name` takes one image; `image-name-specializations` with
  `{"appearance": "dark", "value": …}` is accepted by actool and then **ignored**.
  Compiling with and without it produces byte-identical catalogs.
- The same holds for `is-hidden-specializations`; `fill-specializations` does
  not change the output either; `light-color`/`dark-color` on the fill is
  rejected outright.
- A shipping themed icon (Maccy, Chrome) carries `Image` renditions tagged
  `NSAppearanceNameDarkAqua`. Nothing authorable by hand produces that tag: only
  the system *fill* is themed, and this app's artwork bakes the background and
  the glyph into one opaque tile, so the fill is hidden behind it.

In short: the only appearance dimension a hand-written `.icon` exposes is the
system fill, and an icon whose background is part of its artwork cannot use it.

This is also what the 1.3.3 report looked like in practice. 1.3.3 shipped an
`Assets.car` whose base rendition was the light tile; because no dark rendition
existed, dark mode kept showing the white tile while the running Dock, which the
app draws itself, stayed black.

## What a future version would have to do

To make the bundle icon follow the system, the artwork has to be re-authored in
Apple's model rather than this app's:

- the **background becomes the system fill** (`fill`, left automatic) so macOS
  draws the light, dark, clear and tinted tiles itself, and
- the **glyph becomes a transparent layer** — the same shape
  `DockIconGlyphLayout` already describes, about 65% of the canvas.

That is a visual redesign, not a bug fix: the icon stops being a flat black or
white rounded square and becomes the system's own tile. Icon Composer (the GUI
shipped with Xcode) is the tool Apple expects to be used for it; note that a
hand-authored document cannot express per-appearance *raster* artwork at all,
which is the finding above.

## Changing the icon

`Support/AppIcon.png` is generated, not drawn by hand:

```bash
STATUS_TRIO_APP_ICON_PREVIEW=/tmp/status-trio-app-icon.png \
  swift test --filter AppIconPreviewTests
cp /tmp/status-trio-app-icon.png Support/AppIcon.png
cp Support/AppIcon.png screenshots/status-trio-app-icon-preview.png
```

`AppIconPreviewTests` pins `Support/AppIcon.png` to
`screenshots/status-trio-app-icon-preview.png` byte for byte, so the approved
artwork has to be updated in both places deliberately.

`scripts/build-app.sh` turns that PNG into `AppIcon.icns` with `sips` and
`iconutil` and ships it as `CFBundleIconFile`. There is deliberately no
`Assets.car`: one was shipped from 1.3.3 and removed again when it turned out to
change nothing, and a bundle carrying `CFBundleIconName` without a matching
catalog is worse than one that never had it.
